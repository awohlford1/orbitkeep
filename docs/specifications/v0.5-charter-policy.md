# v0.5 Charter policy specification

Status: SDK and managed-dispatch enforcement implemented
Target release: Orbitkeep v0.5.0

A Charter is a strict, versioned policy document evaluated before governed
actions. The Local Charter is derived from the Silo's effective configuration.
A Keep may additionally supply a signed central Charter. Orbitkeep evaluates
each independently and permits an action only when every applicable Charter
allows it. Local policy can restrict central authority but cannot expand it.
Local-only operation requires no central Charter.

## Policy domains

The v0.5 contract covers provider allow/deny rules, role-specific models,
resource ceilings, filesystem read/write patterns, network hosts, secret
references, Crew roles, required gates, action-specific Clearances, retention
ceilings, and mandatory redaction. Requests declare only the capabilities they
intend to use; a declared capability outside either Charter fails closed with
specific violations.

The existing effective configuration is adapted into a Local Charter without
changing its semantics. Explicitly disabled providers remain denied, empty
model lists remain unrestricted, enabled Crew roles remain bounded, and
retention and redaction invariants remain enforced.

## Trust, rotation, and failure

Central Charters use Ed25519 signatures over canonical JSON. Trusted public
keys are supplied by registration/bootstrap trust, never by the signed
document. Verification rejects unknown keys, tampering, future-issued policy,
and expiry. Acceptance pins the Charter identity and requires monotonically
increasing revisions. Identical same-revision delivery is idempotent; a changed
same revision, lower revision, or different Charter identity is rejected.
Rotating a signing key therefore requires an already trusted overlap key or an
explicit external trust-bootstrap operation.

The command service accepts only signed central policy plus its trusted-key
set. Managed Run dispatch evaluates the central and configuration-derived Local
Charters before creating a Run or Mission Brief. Existing scheduling, role,
model, provider, budget, and gate controls remain defense in depth.

The public boundary is `orbitkeep/policy`, with `charter.schema.json` for
non-TypeScript authoring. Durable central-Charter storage and Relay delivery are
future Keep integration work; callers must persist the last accepted revision
before using monotonic acceptance across process restart.
