# Orbitkeep v0.5 Session Broker and Release Integrity Specification

Status: superseded for user-facing launch by the v0.5 headless Mission control
path. Broker identity and artifact-integrity requirements remain applicable.

## Purpose

This specification closes two release-blocking gaps found after the v0.4.2
Ubuntu UAT:

1. An enforced Claude hook rejected every tool in a directly launched session,
   while Orbitkeep had no interactive launch path capable of supplying trusted
   Mission context.
2. `npm publish` packed the working tree, allowing files outside the intended
   public documentation surface to enter an artifact before they were committed.

## User workflow

The former interactive launcher is retired. After local installation and
setup, the user starts a Mission from the Silo root:

```sh
npx orbitkeep mission start --provider claude
# or
npx orbitkeep mission start --provider codex
```

Orbitkeep owns the terminal interaction and invokes the separately installed,
authenticated provider CLI headlessly. A missing executable returns
`PROVIDER_CLI_NOT_FOUND`; a non-zero provider run returns
`PROVIDER_EXECUTION_FAILED`.

Direct `claude` launch remains fail-closed when the installed Claude integration
is enforced. Its first attempted tool receives
`WORKFLOW_BROKER_SESSION_REQUIRED` with the managed launch command.

## Broker records and identity

Orbitkeep creates an ignored local record at
`.agent-state/control/sessions/<session-id>.json`. It contains:

- record schema version;
- provider and manager/specialist kind;
- stable provider-specific manager-instance identity;
- a digest of the private session capability;
- starting, running, stopped, or failed lifecycle state;
- timestamps and provider process outcome;
- Mission, Operation, and Run bindings when applicable;
- the active ownership fencing token only while needed by a live session.

The private capability is supplied only through the provider child process
environment. It is not written to disk, printed, or included in events. The
fencing token is removed when an interactive session exits normally or with an
observed failure. Provider-specific manager identity is created atomically and
reused on later launches so a restarted Flight Director can recover its Mission.

The session record is ephemeral control state, not canonical Mission history.
Canonical actions and decisions remain in the Flight Recorder and assignment
records.

## Claude authorization

Every Claude `PreToolUse` request is enriched from the secret-bound broker
record. Hook input cannot replace the trusted manager identity, Mission binding,
or fencing token.

Before a Mission is bound, the hook permits only:

- read-only repository discovery through `Read`, `Glob`, `Grep`, and `LS`;
- web discovery through `WebSearch` and `WebFetch`;
- a single `npx --no-install orbitkeep <managed-command>` shell invocation.

Discovery cannot target paths outside the Silo or sensitive framework, VCS,
credential, environment, dependency, or local state paths. Bootstrap shell
commands cannot contain pipelines, redirection, chaining, newlines, command
substitution, or arbitrary executables.
The command must contain exactly one valid, single-quoted JSON object and may
only add the output-redaction flag; root overrides and all other trailing
arguments are rejected.

After `start`, Orbitkeep binds the returned Mission ID and ownership lease to
the broker session. Consequential tools remain blocked until the Flight Plan is
approved or validly waived and Command Authority is `authorized`. Once
authorized, the hook verifies the stable manager owner, current fencing token,
and any referenced running specialist execution before allowing the tool.

A later provider session reuses its provider manager identity. It must use the
normal `ownership-acquire` recovery command when the previous lease has expired;
the CLI then refreshes the broker binding. Cross-manager transfer still requires
the explicit handover workflow and does not transfer a live provider process.

## Attribution

Brokered manager commands default their event actor to the stable manager
instance rather than the generic local-manager placeholder. Explicit Executive
actors on Clearance commands are preserved. Provider session and process IDs
remain provenance and never replace durable framework identities.

## Release integrity

The npm `files` allowlist names the public documentation files individually.
Repository-internal specifications are not distributed in the package unless a
future release explicitly promotes them into the public surface.

`prepublishOnly` runs the complete verification suite and a release preflight
that requires:

- a Git checkout;
- no tracked or untracked working-tree changes;
- the `main` branch at the exact configured upstream commit;
- matching package, lockfile, source, and changelog versions;
- an unused local release tag;
- the explicit packed-file allowlist, required JavaScript exports and TypeScript
  declarations, and artifact size limits.

The package smoke test installs the packed artifact into a fresh consumer,
validates setup and diagnostics, and asserts that internal specifications are
absent. This prevents a locally modified file from silently changing the npm
artifact associated with a reviewed commit.

GitHub Actions executes the same verification gate on Node.js 24 for Windows,
macOS, and Linux. A configured matrix is not evidence of success until every
job passes for the exact release-candidate commit.

## Verification requirements

The v0.5 release gate includes automated evidence for:

- secret-bound lookup and rejection of a wrong capability;
- stable manager identity across sessions, including concurrent creation;
- bootstrap allow/deny classification and path containment;
- rejection of an unbrokered Claude tool request;
- read-only brokered bootstrap access;
- write denial before Clearance and allowance after authorization;
- automatic Mission and fencing-token binding;
- globally ordered concurrent event appends on Windows and Unix-like systems;
- upgrade and rollback from v0.4.2;
- clean packed-consumer installation with the intended file allowlist.

## Known boundaries

This is a local process broker, not a hardened security sandbox. A provider that
has received broad authorized shell access runs with the user's operating-system
permissions. Docker Module isolation, a long-running broker service, encrypted
local secret storage, remote Keep coordination, and centralized revocation are
later roadmap work.

Abrupt termination can leave a stale `running` session record. Session-record
reconciliation and bounded cleanup must be added before Orbitkeep represents
the broker as an unattended, long-running control service. Until then these
small ignored records are diagnostic local state and are not automatically
deleted.
