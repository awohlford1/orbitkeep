# v0.5 workflow engine specification

Status: Ratified model; implementation in progress
Target release: Orbitkeep v0.5.0
Scope: deterministic Operation scheduling, dependencies, gates, budgets,
retries, rework, cancellation, conditional routing, and templates

## 1. Purpose

The workflow engine turns an approved Flight Plan into deterministic Operations
without relying on a Flight Director's prose or provider-specific behavior for
enforcement. Orbitkeep Core remains authoritative for eligibility, lifecycle
transitions, and execution authority.

## 2. Scheduling model

An Operation is represented by the existing task aggregate. Each Operation may
declare required or optional dependencies, an integer priority, and a durable
creation sequence. Eligibility is computed from canonical Mission state.

An Operation is eligible only when:

- its state is `ready`;
- its Mission is `running` and execution authority is `authorized`;
- none of its affected paths are held;
- every required dependency exists and is in one of that dependency's declared
  acceptable states; and
- an Operation concurrency slot is available.

Optional dependencies convey ordering preference and provenance but never block
dispatch. A cancelled required dependency is a terminal dependency failure and
must not be treated as ordinary waiting.

Eligible Operations are ordered by descending priority, ascending durable
creation sequence, then lexicographic task ID. Timestamps are not an ordering
authority. The evaluator is pure and returns both eligible Operations and
machine-readable block reasons.

Graph validation rejects self-dependencies, duplicate edges, missing required
dependencies, and required-dependency cycles. Old task records without
scheduling fields receive deterministic compatibility defaults when restored.

## 3. Enforcement boundary

Both explicit dispatch and automatic dispatch performed while beginning a Run
must call the same eligibility guard. Direct mutation of `.agent-state` remains
unsupported. SDK callers can inspect the scheduler decision through the public
`orbitkeep/scheduling` export.

The implemented foundation covers dependency graphs, deterministic selection,
configured concurrency enforcement, phase-specific required and optional
quality gates, transitive cancellation propagation, canonical persistence, and
dispatch/acceptance enforcement. It also covers Mission and Run resource
budgets and provider-neutral usage observations. CLI parsing is supported through the existing
manager command protocol; no separate interactive scheduler is required.

Cancellation follows required dependency edges transitively and ignores
optional edges. Running affected Operations receive the configured graceful or
force stop request before they are terminalized. An unconfirmed stop becomes an
explicit unknown Run outcome, blocks the affected Operation and Mission, and
holds execution authority. Accepted and closed Operations remain immutable
history.

Required `pre_dispatch` gates block dispatch; required `pre_acceptance` gates
block result acceptance. Optional gates remain diagnostic. Gate outcomes are
`passed`, `failed`, or `waived`; a failed gate may later pass after remediation.
Waivers require Executive authority. Signed gate-waiver receipts are not yet
implemented, so signed-approval mode rejects gate waivers instead of silently
falling back to asserted identity.

## 4. Resource budgets and usage observations

A Mission budget is supplied to `start`; a Run budget is supplied as
`runBudget` to `task-create`. Supported integer limits are input tokens, output
tokens, total tokens, cost in micro-units, and elapsed milliseconds. Mission
budgets may additionally limit the number of Runs. Run budgets reject
`maxRuns`, because a Run is already one attempt.

Each provider measurement is recorded through `usage-record` as an immutable,
idempotent observation bound to exactly one Mission, Operation, and Run. The
observation records provider, model, `observed` or `estimated` provenance,
input, output, cached-input tokens, cost in micro-units, and observation time.
Cached input is a subset of input and is not added again to total tokens.
Orbitkeep does not derive prices from mutable model-name tables.

Mission and Run totals are derived from observations and persisted in canonical
records. An identical observation ID and body is an idempotent retry; reuse of
the ID with different content is rejected. Estimated measurements count toward
limits conservatively. A completed observation exactly equal to a limit remains
valid, but the scheduler blocks a subsequent Run. An observation beyond a hard
limit marks the relevant budget exceeded, blocks the active Operation and
Mission, and holds Command Authority. Active provider-process termination on a
budget signal is not claimed by this slice; cancellation remains an explicit,
observably confirmed control action.

## 5. Retry policy

Every Operation snapshots an effective retry policy at creation. The project
default is `maxAttempts: 1` with no backoff entries, so retries are disabled
unless the project or Operation explicitly opts in. `backoffSeconds` contains
exactly one nonnegative integer delay for each possible retry after the initial
attempt.

A retry is available only after the latest Run has the concrete `failed`
outcome. The failed Operation becomes `blocked`; `execution-retry` idempotently
schedules that exact Run and persists the next-attempt number and not-before
timestamp. The Operation becomes scheduler-visible, but dispatch remains
blocked with `RETRY_BACKOFF_ACTIVE` until the timestamp. Beginning it creates a
new Run with a new execution ID. Exhausted, cancelled, stale, and unknown Runs
cannot be retried, and generic task transitions cannot bypass this workflow.

Run `attempt` is the Operation-wide Run ordinal. `retryAttempt` counts attempts
within the current delivery cycle, while `runKind` distinguishes `initial`,
`retry`, and `rework`. A submitted Mission Report sent to rework begins a new
retry cycle at `retryAttempt: 1`; it does not consume or inherit the preceding
cycle's retry count. Every retry still counts toward Mission Run budgets.

## 6. Conditional routing and reusable workflows

Conditional routing is implemented as durable route records. A route binds one
source Operation to one target Operation and reads exactly one source kind:
latest Run outcome, Operation state, or named gate outcome. Expected values are
validated against the source kind. Only concrete values can be evaluated;
notably, an `unknown` Run is never branch authority.

Route evaluation records both matching and nonmatching observations. A match
may activate a draft target, skip an inactive target, block a draft or ready
target, or cancel an inactive target and its required dependents. Cancellation
that encounters active Runs is rejected so provider interruption continues to
use the explicit, confirmed cancellation workflow. Applied routes are
idempotent, and `skipped` is a terminal Operation state accepted by Mission
closure but treated as failure by required dependencies. Route creation and
evaluation are explicit SDK/manager commands. Automatic route polling remains
outside the local-first v0.5 runtime; the Flight Director evaluates a route
when its declared source has a concrete outcome.

Reusable workflow templates are implemented as strict, versioned portable
definitions. An application atomically validates the graph, enabled Crew roles,
dependencies, gates, retry and budget policy, conditional routes, and optional
path bindings; it then creates ordinary canonical Operations and routes. The
template uses portable keys while the application records their generated
canonical IDs. It also preserves the exact normalized snapshot, SHA-256 digest,
bindings, and version. Reusing an application ID with identical content is
idempotent; conflicting reuse and every invalid template fail without partial
state or events.

Only affected paths are project bindings in v0.5. A template owns its roles and
workflow semantics; provider and model selection remain per-Run policy choices.
Routed targets begin in `draft`, while other Operations begin in `ready` and
remain dependency-controlled. The manager invokes application explicitly
through `template-apply`; applying a template does not bypass Flight Plan
Clearance or automatically dispatch any Crew.

All v0.5 workflow-engine slices persist enough state to survive restart, emit
Flight Recorder events for mutations, reject bypass through alternate SDK
commands, and include adversarial tests.
