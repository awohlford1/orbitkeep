# v0.5 Silo identity and lifecycle specification

Status: Ratified; implementation in progress
Target release: Orbitkeep v0.5.0
Scope: Silo identity, local runtime instances, registration, lifecycle,
diagnostics, migration, and foundational interfaces for later federation

## 1. Purpose

This specification makes the Silo a first-class Orbitkeep runtime boundary. It
defines how one governed repository is identified, how multiple local checkouts
are distinguished, how a Silo joins a Keep and Colony, and how its
administrative, connectivity, and health state is derived and audited.

The design must support local-only use without Mission Control or Relay. It
must also give later platform components a stable identity and lifecycle model
without allowing central coordination to replace local execution truth.

## 2. Goals

- Give each governed repository one durable logical `siloId`.
- Give each local checkout or runtime installation a distinct
  `siloInstanceId`.
- Preserve identity across setup, repair, package upgrade, and process restart.
- Support optional registration into exactly one Keep and at most one Colony at
  a time.
- Expose deterministic lifecycle, connectivity, capability, and health state.
- Define authenticated, idempotent registration and key rotation contracts.
- Keep unregistered Silos fully functional in local-only mode.
- Record all identity and lifecycle mutations in the local Flight Recorder.
- Provide safe behavior for clones, worktrees, forks, corruption, disconnection,
  retirement, and migration from v0.4.2.

## 3. Non-goals

This work does not implement:

- Mission Control.
- A hosted Keep control plane.
- Redis or another production Relay transport.
- Central multi-user identity or RBAC.
- Docker Mission Modules.
- Central event replication or artifact storage.
- Cross-Silo Mission execution.

The specification defines the interfaces those components will consume, but
v0.5 remains independently useful in local-only mode.

## 4. Identity model

### 4.1 Logical Silo identity

`siloId` identifies the governed repository across machines and checkouts. It
uses the portable form `silo-<uuid>` and is created once during setup or the
v0.4.2-to-v0.5.0 migration.

The canonical descriptor is `.agent-workflow/silo.json`. It is intended to be
committed with the repository so clones and worktrees retain the same logical
Silo identity. Setup, repair, and upgrade must preserve a valid existing
descriptor and must never silently regenerate it.

Example:

```json
{
  "schema_version": "1.0",
  "silo_id": "silo-6a7a248d-4b72-4f38-a983-243b773c81c8",
  "created_at": "2026-09-14T16:00:00.000Z",
  "identity_version": 1,
  "origin_hint": {
    "provider": "github",
    "repository": "example/orbitkeep-consumer"
  }
}
```

`origin_hint` is optional, non-authoritative, and contains no credential. It is
used only to warn about likely repository forks or remote changes. Git remotes
alone never establish identity or authority.

### 4.2 Local Silo instance identity

`siloInstanceId` identifies one local checkout and its local Orbitkeep runtime.
It uses `sinst-<uuid>` and is stored at
`.agent-state/.runtime/silo-instance.json`, which remains ignored by Git.

Every newly initialized clone or worktree receives a new instance identity,
while process restarts within that checkout reuse it. The record binds the
instance to the tracked `siloId` and may include a one-way workspace fingerprint
for local duplicate diagnostics. Absolute paths must not be transmitted or
written to ordinary events.

Example:

```json
{
  "schema_version": "1.0",
  "silo_instance_id": "sinst-f95d0322-2f3c-4d39-a366-fced93f63010",
  "silo_id": "silo-6a7a248d-4b72-4f38-a983-243b773c81c8",
  "created_at": "2026-09-14T16:01:00.000Z",
  "last_started_at": "2026-09-14T16:01:00.000Z",
  "instance_version": 1,
  "workspace_fingerprint": "sha256:..."
}
```

### 4.3 Process and provider identities

Process IDs, provider session IDs, provider task IDs, and manager instance IDs
remain provenance or short-lived control identities. None may substitute for a
`siloId`, `siloInstanceId`, registration credential, or Command Authority
fencing token.

### 4.4 Clones, worktrees, and forks

- A clone retains `siloId` and creates a new `siloInstanceId`.
- A Git worktree retains `siloId` and creates a new `siloInstanceId` in that
  worktree's local state root.
- Concurrent instances of one Silo are allowed, but the future Keep applies
  connection and Mission concurrency policy independently to each instance.
- A repository fork initially contains the source `siloId`. Before the fork is
  registered as an independent Silo, its owner must run an explicit identity
  derivation command. Orbitkeep never infers that a changed Git remote means a
  new identity.
- `orbitkeep silo derive` creates a new `siloId`, preserves
  `derived_from_silo_id` as non-authoritative lineage, invalidates any copied
  registration receipt, and creates a new local instance identity.
- Derivation is blocked while Missions are open or the Silo is registered,
  unless registration has first been revoked or explicitly retired.

## 5. Storage model

| Record | Location | Git | Authority |
| --- | --- | --- | --- |
| Logical Silo descriptor | `.agent-workflow/silo.json` | Tracked | Local repository configuration |
| Instance record | `.agent-state/.runtime/silo-instance.json` | Ignored | Local runtime |
| Registration request | `.agent-state/registration/request.json` | Ignored | Local pending intent |
| Registration receipt | `.agent-state/registration/receipt.json` | Ignored | Signing Keep authority |
| Connection observation | `.agent-state/registration/connection.json` | Ignored | Local observed state |
| Capability snapshot | `.agent-state/registration/capabilities.json` | Ignored | Local observed state |
| Health assessment | `.agent-state/registration/health.json` | Ignored | Local derived state |
| Public key metadata | `.agent-state/registration/keys.json` | Ignored | Local plus signed receipt |
| Private signing material | Credential provider | Never tracked | Silo credential provider |
| Lifecycle events | `.agent-state/events/YYYY-MM-DD.jsonl` | Ignored | Append-only local Flight Recorder |

All mutable JSON records use atomic replacement and JSON Schema validation.
Identity and registration mutations use the existing operation-lock and
installation-transaction mechanisms where applicable. Historical events are
never rewritten.

Private key material must not appear in configuration, events, diagnostics,
transcripts, Black Box captures, installation snapshots, or migration evidence.
A `SiloCredentialProvider` interface supplies signing operations. The initial
local-file provider is permitted only for developer-preview use, must request
restrictive host permissions, and causes `doctor` to report `degraded` rather
than `healthy`. Hardened OS or external secret-store providers are later
implementations of the same interface.

## 6. Membership and registration

### 6.1 Cardinality

A Silo may be:

- Unregistered, with no Keep or Colony membership.
- Registered to exactly one `keepId`.
- Registered to zero or one `colonyId` within that Keep.

Changing Keep membership is not an in-place edit. The existing registration
must be revoked or retired, followed by a new registration exchange. Moving
between Colonies within one Keep requires a newly signed receipt.

### 6.2 Registration request

The Silo creates and signs a request containing:

- Request and idempotency IDs.
- `siloId` and `siloInstanceId`.
- Silo public key and key ID.
- Requested `keepId` and optional `colonyId`.
- Capability digest.
- Charter compatibility information.
- Issued-at and expiry timestamps.
- Nonce.

Repeated submission of the same request and idempotency ID must return the same
disposition. Reuse with different content is rejected.

### 6.3 Registration receipt

The Keep authority returns a signed receipt containing:

- Registration ID and version.
- Exact `siloId`, public-key fingerprint, `keepId`, and optional `colonyId`.
- Granted capability bounds.
- Central Charter identifier, version, and digest.
- Status, issue time, expiry or revalidation time, and authority key ID.
- Request idempotency ID.

The Silo validates the signature, scope, time bounds, identity, key fingerprint,
and Charter reference before atomically accepting the receipt. An invalid
receipt is quarantined with its redacted original content and validation error;
it never changes registration state.

### 6.4 Registration transport

Registration uses a `SiloRegistrationClient` interface. v0.5 provides an
in-memory adapter for contract and UAT testing. A configured but unavailable
adapter returns `REGISTRATION_UNAVAILABLE` and leaves the Silo unregistered.
Local-only workflows continue unless Local Charter explicitly requires
registration.

The later Relay implementation may carry registration messages, but the
registration contract is not coupled to Redis or any specific transport.

## 7. Lifecycle model

Silo state is represented by three orthogonal dimensions rather than one
freely mutable status.

### 7.1 Administrative state

```text
unregistered -> registration_pending -> registered -> retirement_pending -> retired
                       |                    |
                       +----> unregistered <-+ (rejected or revoked)
```

- `unregistered`: no accepted registration receipt.
- `registration_pending`: a non-expired request awaits a concrete outcome.
- `registered`: a valid accepted receipt exists.
- `retirement_pending`: retirement intent is recorded but acknowledgement or
  local finalization is incomplete.
- `retired`: terminal registration state. Historical records remain readable.

An unknown registration outcome creates a pending action tied to the concrete
registration request. It cannot be reconciled to `unknown`; reconciliation must
resolve to accepted, rejected, expired, cancelled, or failed.

### 7.2 Connectivity state

```text
offline -> connecting -> connected -> disconnected
             |              ^             |
             +--------------+-------------+
```

- `offline`: no central connection is configured or requested.
- `connecting`: a bounded connection attempt is active.
- `connected`: an authenticated session has been observed and remains within
  its liveness window.
- `disconnected`: a previously requested or established connection is absent,
  expired, or explicitly closed.

A missing Beacon or transport acknowledgement never proves that a remote
process stopped. Connectivity is an observation, not execution outcome.

### 7.3 Health state

- `healthy`: every required local capability and configured integration is
  currently enforced.
- `degraded`: local operation remains safe, but an optional capability,
  hardened credential store, registration connection, or observation is
  unavailable.
- `blocked`: a required capability, identity invariant, Charter validation,
  credential, or safety control is invalid or unavailable.

Health is derived from diagnostics and cannot be set directly by a caller.

### 7.4 Display state

CLI and Mission Control clients may show one summary using this precedence:

1. `retired`
2. `blocked`
3. `degraded`
4. `registration_pending` or `retirement_pending`
5. `connected`
6. `disconnected`
7. `registered`
8. `unregistered`

The underlying three dimensions must remain available in machine-readable
output so the summary cannot hide the reason for the state.

## 8. Disconnected operation

- An unregistered Silo follows its Local Charter.
- A registered but disconnected Silo may continue only within its last valid,
  non-expired central Charter and its Local Charter.
- The effective Charter is the intersection of central bounds and local
  restrictions.
- Disconnection cannot grant a new provider, model, permission, budget,
  Clearance, or consequential action.
- Commands requiring fresh central authority fail closed while disconnected.
- Local work performed while disconnected retains local sequence and
  provenance and is reconciled explicitly after reconnection; no last-writer
  wins merge is allowed.

## 9. CLI contract

All commands retain Orbitkeep's JSON-on-standard-input convention. Agent
managers and automation request stable JSON output with `--json`; interactive
terminals receive a human-readable projection by default. Presentation is not a
separate mutation path.

### `orbitkeep silo status`

Read-only. Returns logical and instance IDs, membership, all three lifecycle
dimensions, display state, capabilities, Charter status, key metadata, latest
connection observation, diagnostic findings, and timestamps. Secrets and
absolute workspace paths are excluded.

### `orbitkeep silo register`

Reserved and not exposed as an operational CLI command in v0.5. The equivalent
SDK service creates or resumes an idempotent registration exchange through an
injected client. It must not overwrite an accepted registration or silently
change Keep or Colony membership. Consequential external submission follows
intent-first logging and the configured bounded retry policy. The in-memory
adapter is limited to contract and UAT testing and must not present itself as a
durable Keep.

### `orbitkeep silo disconnect`

Requests graceful connection closure and records the observed outcome. `force`
may terminate the local connection process but must record an unknown outcome
when remote acknowledgement is absent. It does not revoke registration.

### `orbitkeep silo rotate-key`

Creates a new key through the credential provider and performs a signed
old-key/new-key rotation exchange. The previous key remains accepted only for a
bounded overlap specified by the receipt. Failure before acknowledgement keeps
the old key active. Unknown outcome enters pending reconciliation.

### `orbitkeep silo retire`

Requires explicit Executive Clearance when registered. It blocks new Missions,
attempts bounded registration revocation, records unresolved outcomes, and
preserves all historical records. Retirement never deletes the Silo descriptor,
Mission Archive, or Flight Recorder.

### `orbitkeep silo derive`

Explicitly creates an independent logical Silo from a copied or forked
repository. It is never run automatically and is blocked by open Missions or an
active registration.

## 10. Core interfaces

The v0.5 implementation exposes stable interfaces independent of CLI and
transport presentation:

```ts
interface SiloIdentityRepository {
  getSilo(): Promise<SiloDescriptor | undefined>;
  createSilo(input: CreateSiloInput): Promise<SiloDescriptor>;
  getInstance(): Promise<SiloInstance | undefined>;
  createInstance(siloId: string): Promise<SiloInstance>;
  deriveSilo(input: DeriveSiloInput): Promise<SiloDescriptor>;
}

interface SiloRegistrationRepository {
  getRegistration(): Promise<SiloRegistration | undefined>;
  saveRequest(request: RegistrationRequest): Promise<void>;
  acceptReceipt(receipt: RegistrationReceipt): Promise<void>;
  recordConnection(observation: ConnectionObservation): Promise<void>;
  recordHealth(assessment: SiloHealthAssessment): Promise<void>;
}

interface SiloRegistrationClient {
  register(request: RegistrationRequest): Promise<RegistrationResponse>;
  rotateKey(request: KeyRotationRequest): Promise<KeyRotationResponse>;
  retire(request: RetirementRequest): Promise<RetirementResponse>;
  disconnect(request: DisconnectRequest): Promise<DisconnectResponse>;
}

interface SiloCredentialProvider {
  createKey(keyId: string): Promise<PublicKeyDescriptor>;
  sign(keyId: string, payload: Uint8Array): Promise<Uint8Array>;
  retireKey(keyId: string): Promise<void>;
  assess(): Promise<CredentialProviderAssessment>;
}
```

All implementations receive injectable clocks and ID generators for
deterministic tests. Persistence interfaces perform validation and atomicity;
transport clients do not mutate canonical state directly.

valid and historical data is not rewritten.

## 12. Diagnostics and capability reporting

`orbitkeep doctor` adds checks for:

- Missing, malformed, unsupported, or unexpectedly changed Silo descriptors.
- Missing instance identity and mismatched instance-to-Silo binding.
- Duplicate local instance fingerprints.
- Changed Git origin hints, reported as warnings rather than automatic rekeying.
- Registration receipt signature, scope, time, identity, key, and Charter
  validity.
- Pending registration, key rotation, disconnect, or retirement actions.
- Credential-provider availability and protection level.
- Capability drift since the accepted registration receipt.
- Central and Local Charter compatibility.
- Safe disconnected-operation bounds.

Diagnostics retain the existing literal levels: `enforced`, `observed`,
`instructed`, and `unsupported`. The Silo health projection must not describe an
instructed control as enforced.

## 13. Migration from v0.4.2

The registered migration `migration-0.4.2-to-0.5.0` is reversible until a Silo
accepts central registration.

The migration:

1. Blocks while any Mission or Run is active, consistent with current upgrade
   policy.
2. Creates `.agent-workflow/silo.json` only when absent.
3. Creates `.agent-state/.runtime/silo-instance.json` only when absent.
4. Adds required registration directories without modifying existing records.
5. Updates installation metadata and managed-file manifests.
6. Appends migration evidence and completion events.
7. Does not rewrite existing daily event logs, Mission records, role IDs,
   provider IDs, or ownership state.

If a descriptor already exists, it must validate exactly before migration may
continue. Malformed or conflicting identity is a manual conflict and is never
overwritten by repair or upgrade.

Rollback removes only identity files created by that transaction and only when
they have not changed. Once a signed registration receipt exists, rollback
requires registration revocation or explicit operator resolution so a formerly
registered identity cannot be silently erased.

## 15. Test and UAT matrix

### Identity

- Fresh setup creates one logical and one instance identity.
- Repeated setup, repair, and upgrade preserve both IDs.
- Clone and worktree preserve `siloId` and create unique instance IDs.
- Explicit derivation creates a new Silo and invalidates copied registration.
- Malformed, replaced, or mismatched identities fail safely.
- Concurrent initialization cannot create competing identities.

### Registration and credentials

- Valid signed registration is accepted atomically.
- Wrong Keep, Colony, Silo, key, Charter, expiry, nonce, or signature is
  rejected and quarantined.
- Identical requests are idempotent; conflicting idempotency reuse fails.
- Registration loss, timeout, retry exhaustion, and late response reconcile
  without duplicate effects.
- Key rotation succeeds, fails before acknowledgement, and reconciles an
  unknown outcome without losing the last valid key.

### Lifecycle and disconnection

- Every allowed administrative and connectivity transition succeeds.
- Every forbidden transition returns a stable error and leaves no partial
  mutation.
- Health is derived consistently from the same findings.
- Disconnection never expands authority.
- Retirement blocks new Missions and preserves history.

### Installation and compatibility

- v0.4.2 upgrade and safe rollback pass.
- Active work, identity conflicts, and accepted registration block unsafe
  migration or rollback.
- Empty, partial, customized, malformed, and legacy repositories retain current
  transactional guarantees.
- Windows, macOS, and Linux qualification passes.

### Live UAT

For each supported provider configuration, capture redacted console input and
output, canonical identity and registration records, Flight Recorder events,
pending and quarantine behavior, and final cleanup state. A scenario passes
only when user interaction, provider interaction, state, evidence, and outcome
all agree.

## 16. Acceptance criteria

The specification is implemented when:

- A Silo and every local instance have durable, unambiguous identities.
- Local-only v0.4.2 behavior remains operational after migration.
- Registration is authenticated, idempotent, atomic, and transport-neutral.
- Lifecycle state is derived from explicit administrative, connectivity, and
  health dimensions.
- Clone, worktree, fork, corruption, disconnection, rotation, retirement, and
  rollback behavior is deterministic and tested.
- No central receipt, connection, process identifier, or Git remote can bypass
  Charter evaluation or Command Authority.
- All mutations have schema-valid canonical records and append-only events.
- Full unit, integration, adversarial, migration, cross-platform, package, and
  live UAT gates pass.

## 17. Ratified implementation decisions

1. `.agent-workflow/silo.json` is committed by default. Local checkout identity
   remains ignored in `.agent-state`.
2. Setup may derive a sanitized, non-authoritative `origin_hint` from a
   recognizable Git remote. Credentials, query strings, fragments, host-local
   paths, and the original remote URL are never stored.
3. v0.5 exposes the credential-provider interface and may include a
   developer-preview local provider. That provider is explicitly degraded;
   production health requires a hardened provider.
4. `orbitkeep silo derive` is the public command for intentionally creating an
   independent logical identity from a fork or copy.
5. Retirement is terminal for a `siloId`. Restoration requires derivation or a
   future separately specified recovery lifecycle; callers cannot mutate a
   retired Silo back to active.
